# Архитектура

Обновлён: 24.09.2026

## Стек

- **TypeScript**, `strict` и `noUncheckedIndexedAccess` — те же настройки, что у приложений: ядро компилируется их `tsc` внутри их дерева
- **React** — только в `ui/` и `screens/`; `core/` без React
- **IndexedDB** — хранилище на устройстве; **GitHub API** — синхронизация через приватный репозиторий данных приложения
- **Service worker** — свой, `workbox-*` для кеша, собирается приложением через `injectManifest`
- **Тесты** — Vitest, IndexedDB в node — `fake-indexeddb`
- Своей сборки, своего сайта и своих зависимостей времени выполнения у ядра нет. `package.json` — только для тестов и типов (Я-02)

## Как ядро живёт в приложении

Корень этого репозитория — это `src/shared/` приложения (Р-46, Р-47 «Трапезы»; Я-02):

```
<приложение>/
  src/
    shared/            ← подмодуль FamilyCore, корень этого репозитория
      core/            механика: без React, без приложения
      ui/              общие компоненты и хуки
      screens/         экраны-инфраструктура
      sw.ts            работник
      styles.css       каркас стилей
      scripts/         иконки, фабрика конфига Vite, tsconfig для extends
      docs/ CLAUDE.md package.json …   ядра; приложению не нужны, но лежат рядом
    app/
      config.ts        AppConfig приложения
      model.ts         типы записей, хранилища, миграции
      core.ts          createDb(config), createSync(config, db)… → готовые db, sync, layout, importing
    modules/ screens/ registry.ts notify.ts app.tsx …   приложение
```

Код приложения импортирует готовые `db` и `sync` из `app/core.ts`, общие компоненты — из `shared/ui/…`.

## Шов: конфиг и фабрики

**Ядро про приложение не знает** (Р-47 «Трапезы»). Всё, что у приложений разное, приходит одним объектом `AppConfig`:

| Поле | Что даёт |
|---|---|
| `name` | имя приложения: сообщения коммитов, тексты ошибок, README данных, промпт импорта |
| `dbName` | имя базы IndexedDB; не меняется никогда |
| `schemaVersion`, `migrations` | версия схемы и шаги; ядро номера не диктует |
| `stores`, `v1Stores`, `indexes` | синхронизируемые хранилища, замороженная раскладка версии 1, индексы сверх `updatedAt` |
| `places` | раскладка записей по файлам репозитория данных: одним файлом, по месяцам или по годам (Я-09) |
| `storeNotes` | что лежит в файлах хранилища — строки README данных |
| `importFormat`, `promptRules` | строка `format` файла импорта и свои правила промпта |
| `about.data`, `about.privacy`, `about.sources` | предмет приложения словами: что за данные, почему репозиторий данных приватный, откуда данные для импорта |
| `summary` | необязательно: функция среза итогов `(data, day) → { periods, attention }` по живым записям и дню расчёта (Я-16, Я-17); нет — нет `summary.json` |

Поля сверх этой таблицы появляются только с причиной, записанной здесь же, и должны иметь смысл для любого приложения семьи.

**`about` — сверх Р-47 «Трапезы».** README данных и промпт импорта у «Делу Время» и «Трапезы» различались не только именем, но и тремя фразами о предмете: «учёт времени, план дня, заметки» против «учёт еды: что съедено, в каком приёме». Имя ядро не склоняет: тексты говорят «приложение «Трапеза»», а не «данные «Трапезы»».

**Правила промпта.** Свои правила приложения (`promptRules`) идут первыми, за ними — общие правила ядра (`COMMON_PROMPT_RULES`: разделы без данных не писать, один блок JSON, список сомнений после). Нумерует ядро.

**Исходы импорта** (Я-07). Разбор приложения отдаёт `ImportPlan`: `writes` — что ляжет в базу; счётом словами — `added` (новое), `changed` (изменится уже имеющееся), `removed` (уйдёт надгробием); `skipped` — повторы; `notes` — загрузится, но стоит посмотреть; `issues` — не попадёт. Что в `writes` новое, что правка, что надгробие, — говорит приложение: ядро записи со слепком не сличает. Сводку и запись по кнопке делает `ImportSummary` — на экране `ImportRecords` и там, где файл импорта у приложения появился сам.

**`indexes` заморожен вместе с `v1Stores`** (Я-08). `createStores` заводит индексы конфига только на свежей базе и только у хранилищ версии 1: дописанный позже индекс появится у новой установки и не появится у давней. Индекс после первого релиза — шагом миграции. Читать по индексу — `db.getByIndex(store, index, ключ | { from, to })`; индекс ищется в базе на устройстве, а не в конфиге.

**`summary` — сверх Р-47 «Трапезы»** (Я-16): срез итогов для метаприложения пишет проход синхронизации, а считает приложение (Я-11). Поле имеет смысл для любого приложения семьи и необязательно: приложения переходят на срез по одному.

**`checkConfig`** проверяет конфиг на старте, в `createDb`: `stores` перечисляет все хранилища таблиц без повторов, `v1Stores` — из `stores`, имя не совпадает с локальным хранилищем, место хранилища — не `summary.json` (Я-16), миграции — в пределах версий. Ошибка здесь иначе тихо потеряла бы хранилище при синхронизации.

`AppConfig` обобщён по таблице «хранилище → тип записи» приложения: `db.get('intake', id)` у «Трапезы» возвращает `Intake`, а ядро не знает, что такое `Intake`.

**Фабрики:**

| Фабрика | Что возвращает |
|---|---|
| `createDb(config)` | `db`: чтение, запись с тремя происхождениями, слияние, очередь `dirty`, `settings`, `meta`, слепок, миграции |
| `createLayout(config)` | раскладка: записи ↔ файлы, `meta.json`, README данных |
| `createSync(config, db)` | проход синхронизации, состояние для экрана, автозапуск |
| `createImporting(config)` | разбор файла импорта и промпт |

Чистые функции без параметров приложения (`dates`, `id`, `github`, `feed`, помощники разбора полей импорта) остаются обычными экспортами.

**Общий интерфейс получает `db` и `sync` React-контекстом** (Я-03). Приложение один раз оборачивает дерево в `CoreProvider`; хуки и компоненты ядра берут `useCore()`. Чистые модули `ui/` и работник получают `db` аргументом. Код приложения — вкладки, «Что нового», строки ленты, разделы импорта, правило напоминания — приходит **пропсами и аргументами**, не импортом.

**Правила, которые соблюдаются жёстко:**

- `core` не знает ни `ui`, ни `screens`, ни React
- Ничто в ядре не импортирует файлы приложения. Проверка: ядро собирается и проходит тесты в этом репозитории, где приложения нет
- К хранилищу — только через `db`, созданный `createDb`. `indexedDB` упоминается только в `core/db.ts` и тестах
- Работа с GitHub спрятана в `core/github.ts` и `core/sync.ts`
- Логика вне компонентов: расчёт — чистые функции с тестами, экраны тестами не покрываются

## Как приложение подключает ядро

Чеклист перевода (Р-49 «Трапезы»: отдельной веткой, одним коммитом-переездом, без изменения данных). Имена — у «Трапезы»; у другого приложения — свои.

1. **Подмодуль** — `git submodule add https://github.com/goigolden88/FamilyCore.git src/shared`; в `deploy.yml` у `actions/checkout` — `submodules: true`. В `src/shared` `npm install` не запускается (Я-02)
2. **`src/app/model.ts`** — из `core/model.ts` приложения: типы записей, `RecordKind`, таблица `StoreRecord` (она и есть `R` для `AppConfig<R>`), миграции. `Base` и `Migration` — импортом из `shared/core/model.ts`
3. **`src/app/config.ts`** — `AppConfig<StoreRecord>`: `name`, `dbName`, `schemaVersion`, `migrations`, `stores`, `v1Stores`, `indexes`, `places`, `storeNotes`, `importFormat`, `promptRules`, `about`. Значения — буквально из прежних `DB_NAME`, `SCHEMA_VERSION`, `SYNCED_STORES`, `V1_STORES`, `INDEXES`, `PLACES`, `ABOUT`, `IMPORT_FORMAT`, правил промпта и текстов README. Место по годам — `{ split: 'year', dir, dateOf }` (Я-09): папка и дата — те же, что у прежнего `PLACES`, иначе файлы в репозитории данных станут чужими
4. **`src/app/core.ts`** — `export const db = createDb(config)`, `sync = createSync(config, db)`, `layout = createLayout(config)`, `importing = createImporting(config)`. Код приложения берёт `db` отсюда, а не из `core/db.ts`; функции синхронизации — методами `sync`
5. **`app.tsx`** — дерево в `<CoreProvider value={{ config, db, sync }}>`; `<Layout tabs={TABS} />`
6. **Вызовы, у которых появились аргументы:** `useWhatsNew(base, CHANGES)`; `useFirstRun(own)` — хранилища данных человека (у «Трапезы» — все `stores`, у «Делу Время» — не все), и тот же список — в `isEmptyBase(counts, own)`, если приложение зовёт его само; `useFeed(feedItems)`; `<ImportRecords planImport importPrompt intro onChanged />`, а файл импорта, появившийся у приложения сам, — `<ImportSummary text planImport onApplied onCancel />` (Я-07); `listenErrors(db.settings)` в `main.tsx`; `readErrors`/`clearErrors` — через `ReportBug` ядра
   - **Реестр и разделы импорта — по таблице хранилищ приложения:** данные слепка — `Snapshot<StoreRecord>['data']`, итог разбора — `ImportPlan<StoreRecord>`, а не свои повторы этих типов (перевод «Делу Время», 24.09.2026)
   - **Строка ленты** — `FeedItem` с `kind` строкой; подпись вида — своей `kindLabel(kind: string)`: ядро видов не знает, незнакомый вид подписывается как есть. Порядок ленты — ядра: без даты — внизу (Р-61 «Делу Время»). Показать группу без даты иначе — дело экрана приложения: `groupFeed` отдаёт её последней, и экран вправе поставить её, где ему нужно
7. **`src/changes.ts`** — остаётся список `CHANGES`; `Change`, `unseenChanges`, `latestChange` — из `shared/screens/changes.ts` (Я-06)
8. **`src/notify.ts`** — `export const reminders = createReminders(db.settings, { topics, idle })`: `topics(day)` — свои темы (у «Трапезы» одна, ключи `DAY_KEYS`), `idle` — свой текст «Напоминать не о чем». «Настройки» зовут `reminders.checkReminder`, `readWindow`, `readWakes` и прочее
9. **`src/sw.ts`** — точка входа работника: `startWorker({ remind: (registration) => reminders.remind(registration) })`
10. **`src/styles.css`** — импортируется после `shared/styles.css`; в нём остаётся всё, чего нет в каркасе, и свой `:root` с акцентом
11. **`vite.config.ts`** — `defineConfig(familyVite({ base, name, description, shortcuts }))`; поля манифеста сверх этих (у «Делу Время» — `share_target`) — через `manifest` у `familyVite`, а не правкой фабрики; **`tsconfig.json`** — `extends: "./src/shared/tsconfig.base.json"`; **`scripts/icons.mjs`** — свои фигуры и `writeIcons`
12. **`vite-env.d.ts` приложения** — объявления `__BUILD_TIME__` и `periodicSync` убрать: они в `shared/vite-env.d.ts`, повтор `declare const` не соберётся

Тексты, которые у приложения поменяются сами: ошибки слепка и `meta.json` говорят «приложение «Трапеза»» вместо «Трапезы», README данных — «# Данные приложения «Трапеза»». README в репозитории данных уже лежит и не переписывается (Р-69 «Делу Время»).

## Договор семьи

Р-51 «Трапезы». Договор — то, на что опирается метаприложение семьи и что обязано совпадать у всех приложений. Он и **код** (типы и механика ядра), и **этот раздел**. Раньше он был абзацем в `02-Архитектура` каждого приложения; теперь приложения ссылаются сюда и пишут у себя только то, чем обязаны.

**Правка договора — решение Я-NN и релиз на все приложения сразу.** Тихо в одном приложении договор не меняется.

### `Base` — общая часть каждой записи

```ts
type Base = {
  id: string          // ULID, генерируется локально; приложение вправе держать справочники с id из названия
  updatedAt: string   // ISO 8601, время последнего изменения записи
  deleted?: boolean   // метка удаления, не вычищается никогда
}
```

### Слияние

По каждой записи отдельно, по `id`: побеждает версия с более поздним `updatedAt`. Удалённые остаются надгробиями навсегда: вычистишь — второе устройство воскресит.

### `FeedItem` — строка ленты

```ts
type FeedItem = {
  kind: string        // вид записи приложения: 'intake', 'note', 'time'…
  id: string          // id записи; ключ строки — вид вместе с id
  date: string        // ГГГГ-ММ-ДД, ГГГГ-ММ или как лежит; пусто — даты нет
  title: string
  detail: string
  link?: string       // путь хеш-роутинга приложения
  extra?: string      // ищется, но не показывается
}
```

Строки собирает `registry.ts` приложения, форму задаёт ядро.

### Раскладка репозитория данных

```
meta.json                 { schemaVersion }
<хранилище>.json          справочник или малое хранилище — одним файлом
<папка>/ГГГГ-ММ.json      записи по месяцам, месяц — по дате записи
<папка>/ГГГГ.json         записи по годам, год — по дате записи (Я-09)
<папка>/undated.json      записи без разбираемой даты
summary.json              срез итогов (Я-16): пишет проход, приложение не читает
README.md                 кладётся приложением, если его нет; дальше не трогается
```

- Файл — JSON-массив записей, ключи отсортированы, записи — по `id`, отступ два пробела, перевод строки в конце. Одинаковые данные — побайтно одинаковый файл
- Нарезанное хранилище режется **либо** по месяцам (`split: 'month'`), **либо** по годам (`split: 'year'`), в одной папке — одна нарезка. Дата записи — день `ГГГГ-ММ-ДД` или месяц `ГГГГ-ММ`; год в имени — её первые четыре знака. Нет даты или не читается — `undated.json`
- **Нарезка места после первого релиза не меняется** — ни вид, ни папка, ни путь (Я-09). Прежние файлы стали бы чужими: копия осталась бы на сервере, а записи из неё не дошли бы до свежего устройства. Смена нарезки — миграция репозитория данных
- Файлы, которых нет в раскладке приложения, не читаются и не трогаются; файл чужой нарезки в папке хранилища — тоже
- Своя таблица мест — `places` в `AppConfig` приложения

### `schemaVersion`

- Лежит в `meta.json` репозитория данных, в хранилище `meta` на устройстве и в файле-копии
- **Репозиторий новее приложения** — синхронизация останавливается со словами «обнови приложение», файлы не трогаются
- **Старее** — принимается, если между версиями нет шага с `additive: false`
- Номер и шаги у каждого приложения свои — поля конфига; ядро номера не диктует

### `Migration`

```ts
type Migration = {
  to: number          // на какую версию переводит
  note: string        // что делает и зачем
  additive: boolean   // только добавляет: хранилище, индекс, необязательное поле
  run: (db: IDBDatabase, tx: IDBTransaction) => void   // синхронно, внутри транзакции обновления
}
```

Свежая база строится в раскладке версии 1 (`v1Stores`) и доезжает до текущей теми же шагами, что и база установленной копии. Шаг сам создаёт своё хранилище и индексы; `v1Stores` после первого релиза заморожен.

### Файл-копия

```
{ schemaVersion, exportedAt, data: { <хранилище>: [записи] } }
```

Все синхронизируемые хранилища вместе с надгробиями. `settings` не входит: там токен.

### Устройство и origin

- Все приложения семьи живут на одном origin `goigolden88.github.io`. IndexedDB общая на origin и различается только именем: **`dbName` у каждого приложения свой** — `dnevniki`, `deluvremya`, `trapeza`, `zloty`
- Кеши работника разведены scope'ом; разрешение на уведомления и квота — общие на origin
- `settings` не синхронизируются никогда: в них токен и состояние устройства

### Срез итогов (Я-11, Я-16…Я-19)

Машинный срез итогов приложения для метаприложения. `FeedItem` — текст для человека, считать по нему нельзя; срез — числа с основаниями. Форма — здесь и в коде: типы, отрезки и проверка — `core/summary.ts`, запись — проход `core/sync.ts`.

**Как приложение заводит срез**

1. Обновить указатель ядра
2. Чистая функция `summary(data, day): SummaryBody` — рядом с функциями итогов приложения, с тестами. `data` — живые записи всех синхронизируемых хранилищ, без надгробий; `day` — день расчёта. `settings` устройства не читать
3. Отрезки — `summaryPeriods(day)`, ровно четыре и в том же порядке; не считаемый — `metrics: { unknown: UNKNOWN.notProvided, text }`
4. Поле `summary` в `AppConfig`. Проверка в тестах приложения — `checkSummary(buildSummary(summary(data, day), data, day))` на своих данных
5. Ключи и подписи — в свой `02-Архитектура`, состав — в таблицу ниже сессией ядра

Упавшая функция или кривая форма не ломают синхронизацию: данные уезжают, среза нет, ошибка — в журнал ошибок устройства, одна и та же — один раз. Прежний срез на сервере остаётся со своим днём расчёта.

**Где лежит и как читается** (Я-16)

- `summary.json` в корне репозитория данных приложения. Пишет его проход синхронизации ядра из тех же данных, из которых собираются файлы хранилищ, чистой функцией приложения. Нет функции — нет файла
- Приложение срез не читает: это не файл хранилища, `storeOf` его не знает. Отправляется, только если разошёлся с лежащим
- **Считается только из синхронизируемых записей и дня расчёта**, без `settings` устройства: одинаковые данные в один день — побайтно одинаковый файл, иначе устройства переписывают его друг за другом
- Читает метаприложение — fine-grained токеном только на чтение к репозиториям данных семьи; имена репозиториев — в его настройках, не в коде

**Форма** (Я-17)

```ts
type Summary = {
  format: 1
  computedOn: DateStr           // посчитано: день расчёта
  lastEdit: DateStr | null      // по записям по: день самой поздней правки записи
  periods: PeriodSummary[]      // всегда четыре: прошлая и идущая неделя, прошлый и идущий месяц
  attention: Attention[]
}

type PeriodSummary = {
  grain: 'week' | 'month'       // неделя с понедельника, календарный месяц (Я-12)
  from: DateStr
  to: DateStr
  through: DateStr | null       // неокончательный итог: число верно по это число; null — окончательный
  metrics: Metric[] | Unknown   // отрезок не считается — прямо, с причиной
}

type Metric = {
  key: string                   // машинное имя, устойчиво между срезами
  label: string                 // подпись для человека
  value: Value
  basis: string                 // основание словами: «учёт в 6 днях из 7»
}

type Value =
  | { n: number; unit: 'count' | 'minutes' | 'days' | 'kcal' | 'km' | 'share' }
  | { money: number; currency: string }      // целое в минимальных единицах, код ISO 4217
  | { verdict: 'met' | 'failed' | 'open' }   // 'open' — «не ясно»; вердикт даёт только хозяин
  | Unknown

type Unknown = { unknown: string; text: string }   // причина кодом и словами

type Attention = {
  key: string
  label: string                 // нейтральная подпись, без названий (Я-14)
  count: number | null
  day: DateStr                  // к какому дню относится
  link: string                  // путь хеш-роутинга приложения
}
```

- **Основание — у каждого показателя.** «Не известно» — не ноль и не `null`, а код причины со словами. Общие коды: `not-provided` — приложение этого пока не считает; `no-data` — записей нет; `not-enough` — меньше порога. Свои коды приложение заводит само
- **Отрезок, которого приложение пока не считает, присутствует** и говорит `not-provided`. Истории в срезе нет: прошлое пересчитывается задним числом
- **Деньги** — целым в минимальных единицах с кодом ISO 4217, у каждого числа
- **Правка формы — решение Я-NN и новый `format`**

**«Требует внимания»** (Я-18). В срезе — закончившиеся дни и состояния с днём, к которому относятся. Всё про «сегодня» — напоминаниям самих приложений. Текст темы в срез не идёт.

**Что не идёт никогда:** свободный текст человека (Я-14), имена людей (Я-13), название эпизода болезни, симптомы, `note`, `comment` (Я-19). Названия и суммы — только в составе ниже.

**Потребитель показывает, а не досчитывает** (Я-15, предварительно): ни серий, ни средних на день, ни цвета, ни вердикта сверх данного, ни сложения строк разных приложений. Сопоставление строк соседей — по группе, настройкой человека у метаприложения (Я-19).

**Состав — первый, промежуточно** (Я-19). Названный потребитель — недельная сводка метаприложения (Я-12). Ключи и подписи выбирает приложение; правка состава — правка договора.

| | Отрезки | Показатели | «Требует внимания» |
|---|---|---|---|
| «Делу Время» | неделя, месяц | минуты по группам и фон отдельно, основание — `days` из `elapsedDays` (Р-43, Р-81 «Делу Время»); счёты плана и факта без текстов; нормы недели — вердиктом `met` / `failed` | обзор прошлой недели не проведён |
| «Трапеза» | неделя; месяц — `not-provided` до решения «Трапезы» | порции, записи, `loose`, `assumed`; ккал с основанием `KcalSum`, среднее на день учёта; нормы — вердиктом с `open` и правилом `minDays`/`maxDays` в основании; основание недели — `logged` из `elapsed` | вчерашние пропуски приёмов, без отметок «не было» |
| «Дневники» | неделя, месяц | дни болезни в промежутке и счёт эпизодов — без названий; тренировки — счёт, минуты и км с оговоркой в основании; контент — начато, досмотрено, брошено по промежутку, неделя — `month-precision` | открыт ли эпизод и с какого дня; число просроченного в циклах; число зависшего в «смотрю» |
| «Злотые» | месяц; неделя — `not-provided` | ступень 1 Я-13: есть ли записи, `through` — по какое число доведены выписки, сколько регулярных ждёт, день последнего снимка капитала. Ступени 2 и 3 — не просит никто | за прошлый месяц нет записей; регулярные ждут |

**Что приложения соблюдают в новых функциях и правках уже сейчас:**

- **Итоги считает приложение — хозяин данных, чистыми функциями с тестами** (Я-11). Итог, который склеивает экран, для среза придётся выносить (вычитка «Злотых»): новый итог — сразу чистой функцией
- **Приложения друг о друге не знают.** Факты соседей показывает метаприложение, приложение даёт на него ссылку (Я-12). Чужой репозиторий данных и чужую базу IndexedDB приложение не читает
- **Противоречие с этим разделом решается не на месте в приложении,** а сессией ядра, решением Я-NN

## Версионирование схемы

Относится к приложению, механика — ядра. `schemaVersion` и `migrations` — поля `AppConfig`. Заводятся с первого дня, миграции пишутся сразу. Файл-копия отставшей схемы отвергается, только если между версиями есть шаг с `additive: false`. Устройство на старой версии, увидев схему новее в репозитории, останавливает синхронизацию.

**Схемы у самого ядра нет.** Правка ядра, меняющая то, что лежит в базе или в репозитории данных, — это правка договора (выше), а не миграция одного приложения.
