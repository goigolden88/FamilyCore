### Я-01 · Решения ядра нумеруются «Я-NN»; чужие «Р-NN» в коде получают хозяина
18.09.2026

Повод: открытый вопрос «Трапезы» — «как `FamilyCore` нумерует свои решения» (Р-43, Р-49 «Трапезы», «Цена» п. 2). Первое решение ядра.

**Как было.** В коде, скопированном из «Делу Время», около 170 ссылок «Р-NN»: `core/dates.ts` говорит «неделя — с понедельника (Р-41)» — это Р-41 «Делу Время». «Трапеза» держала правило «голый Р-NN в файлах ядра — чужой» (её Р-43), но номера уже пересеклись: у неё свой Р-41 появился 18.09.2026. В общем репозитории у этих номеров хозяина нет вовсе.

**Решено.**

- Решения ядра — **«Я-NN»**: Я-01, Я-02… — в `docs/05-Решения.md` этого репозитория
- Решение приложения — **«Р-NN» с хозяином**: «Р-41 „Делу Время“», «Р-47 „Трапезы“». Голого «Р-NN» в ядре нет
- Унаследованные ссылки получают хозяина **отдельным коммитом, только комментарии**, сразу после коммита-копии и до выноса. Хозяин проверяется по `05` «Делу Время» на `d86f0aa`, а не на глаз: часть ссылок там — решения «Дневников»
- Правило, которое ядро меняет, получает своё Я-NN со ссылкой на прежнее; правило, которое ядро только несёт, остаётся со ссылкой на родное решение

Выбор человека из четырёх, рекомендация.

**Почему.** Ядро лежит внутри каждого приложения, в `src/shared`. В одном дереве будут и «Р-41» приложения, и ссылки ядра, и отличить их обязан сам текст ссылки, а не путь к файлу. Префикс кириллицей читается в русских комментариях как слово: «Я» — ядро.

Отвергнуто:
- **«FC-NN»** — то же самое, но латиница посреди русского текста;
- **свои «Р-NN» с Р-01** — единообразно с семьёй, но в одном дереве два разных Р-41, то есть ровно та беда, от которой уходим;
- **без ссылок в коде** — «почему» уходит только в `docs/`, связь строки с решением теряется, а 170 ссылок вычищаются впустую.

**Цена.** Коммит комментариев в ~50 файлах — дифф к `d86f0aa` растёт не по делу. Зато он отдельный и пуст по коду: в диффе выноса комментарии не мешают. Ссылки вида «Р-NN „Делу Время“» длиннее голых.

### Я-02 · Корень репозитория — точка монтирования `src/shared`; `package.json` ядра — только для тестов и типов
18.09.2026

Повод: Р-47 «Трапезы» ставит подмодуль в `src/shared/` с `core/` и `ui/` внутри. Отсюда форма самого репозитория.

**Решено.**

- Код лежит **в корне** репозитория: `core/`, `ui/`, `screens/`, `sw.ts`, `styles.css`, `scripts/`. Рядом — `docs/`, `CLAUDE.md`, `package.json`, `tsconfig.json`, настройки тестов. Всё это приезжает в `src/shared` приложения
- **`package.json` без `dependencies`.** Только `devDependencies` для тестов и типов: `typescript`, `vitest`, `fake-indexeddb`, типы React, `react`, `react-router-dom`, `workbox-*`, `vite` и `vite-plugin-pwa` для типов фабрики и работника
- **Версии — ровно те, что в `package-lock.json` «Делу Время» на `d86f0aa`**, записанные точными, без `^`: иначе типы в ядре и в приложении разойдутся
- **`npm install` внутри `src/shared` приложения не запускается никогда.** Иначе импорт `react` из `src/shared/ui` найдёт `src/shared/node_modules/react` раньше приложения, и на странице окажутся две копии React

**Почему.** Иначе путь внутри подмодуля (`src/shared/src/core/…`) расходился бы с деревом, записанным в Архитектуре «Трапезы», а подмодуль нельзя подключить подпапкой.

Отвергнуто: **код в `src/` репозитория** — `src/shared/src/core` в приложении; **отдельный репозиторий под документы** — второй источник истины.

**Цена.**

1. `docs/`, `CLAUDE.md`, тесты ядра видны внутри приложения. Тесты ядра увидят `tsc` и `vitest` приложения: включать их там или исключить — решается при переводе «Трапезы» (передача Б2).
2. Правило про `npm install` держится памятью; нарушение ловится прогоном приложения (две копии React ломают хуки сразу).

### Я-03 · Общий интерфейс получает `db` и `sync` React-контекстом; код приложения — пропсами
18.09.2026

Повод: разбор `d86f0aa`. Р-47 «Трапезы» делает фабриками четыре файла `core/`, но одиночку `db` импортируют ещё восемь общих файлов: `useFold`, `report`, `useFirstRun`, `useWhatsNew`, `useFeed`, `ImportRecords`, `notify` и `sync`; к `sync` так же привязаны `useSync`, `syncDot`, `SyncSettings`, `backup`. Когда `db` создаёт приложение, им негде его взять. Уточняет Р-47 «Трапезы».

**Решено.**

- **Хуки и компоненты ядра** берут `db`, `sync` и `config` из React-контекста: приложение один раз оборачивает дерево в `<CoreProvider value={…}>`, внутри — `useCore()`. Вызовы `useFold(id)`, `<Fold>` и прочих у приложений не меняются
- **Чистые модули** (`ui/report.ts`, `ui/backup.ts`, механика напоминаний, работник) получают `db` и что им нужно **аргументом** или собираются фабрикой
- **Код приложения** — вкладки `Layout`, список `changes` для «Что нового», строки ленты и разделы импорта из `registry.ts`, хранилища первого запуска, правило напоминания — приходит **пропсами и аргументами**, а не импортом

Выбор человека из трёх, рекомендация.

**Почему.** Контекст — обычный путь React передать объект, созданный снаружи: зависимость видна в коде (провайдер в `app.tsx`), а цена переезда у приложений минимальна — меняется один файл, а не каждый вызов `useFold`.

Отвергнуто:
- **фабрики на всё** (`createUi(core)` возвращает готовые хуки) — полностью явно, но ещё один файл-посредник и правка каждого импорта `Fold`/`useFold` в четырёх приложениях;
- **регистрация `bindCore(core)`** — `app/core.ts` кладёт `db` в модуль ядра, дальше всё как было. Дешевле всего при переезде, но это невидимая зависимость, ломающаяся порядком импортов, — ровно то, за что Р-47 «Трапезы» отверг алиас.

**Цена.**

1. Хук ядра вне `CoreProvider` не работает; `useCore()` падает с внятным текстом, а не молча.
2. Работник и `notify` живут вне React — у них свой путь, аргументом; двух способов получить `db` в ядре два, и это надо помнить.
3. У `app.tsx` каждого приложения появляется провайдер.

### Я-04 · Ядро проверяет себя само: `npm test` и `tsc` на каждый пуш
18.09.2026

Повод: ядро стало эталоном для четырёх приложений (Р-49 «Трапезы»), а своей сборки и сайта у него нет — красное ядро иначе обнаружится только при обновлении указателя в приложении.

**Решено.** `.github/workflows/test.yml`: `npm ci`, `npm run typecheck`, `npm test` на пуш и пул-реквест. Итог — по коду выхода. Выбор человека, рекомендация.

Отвергнуто: **только локальная проверка перед пушем** — так живут приложения, но у приложения поломку видно сразу на сайте, у ядра — нет.

**Цена.** Ещё один workflow на обслуживании; зелёный CI ядра не значит, что приложения собираются: это проверяет только их собственный CI после обновления указателя.

### Я-07 · У `ImportPlan` — заметки, правки и удаления; сводка импорта — отдельным компонентом `ImportSummary`
23.09.2026

Повод: находки «Злотых» (их `06-Процесс`, «Шаблоны»; Журнал «Злотых», 20–23.09.2026), сверенные через `git show` на `4b303ed`. Меняет правило, которое ядро несло от Р-60 «Дневников»: «импорт только добавляет».

**Как было.** У разбора раздела два исхода: запись попадёт в базу (`writes`, посчитана в `added`) или нет (`issues`). У «Злотых» импорт делает больше, и сказать об этом ему нечем:

1. **Сообщение — отказом.** «Округление» (учёт и капитал) и «итог периода заменён операциями» лежат в `issues`: сводка пишет «не попадёт в базу: N», а записи попадают. Повод в просьбе назван «склейкой переводов» — её убрал Р-19 «Злотых», но беда та же
2. **Правка — молча.** Сошедшаяся сверка ставит счёту `loadedThrough` (Р-26 «Злотых»): запись идёт в `writes`, но ни в `added`, ни в `issues` её нет
3. **Удаление — отказом.** Итог периода, который заменили операции (Р-02 «Злотых»), уходит надгробием через `writes`, а называется в `issues`. Кнопка «Загрузить N» считает надгробие вместе с добавленным
4. **Общий абзац лжёт.** `ImportRecords` обещает «импорт только добавляет: то, что уже есть, не перезаписывается» — у «Злотых» это неправда дважды
5. **Готовый текст негде показать.** «Подтянуть курсы» получает от источника тот же файл импорта, но сводки ядра для него нет — у кнопки своя, вторая, поверх той же `planImport`

**Договор семьи не затронут.** `ImportPlan` живёт между разбором приложения и экраном ядра, на миг сводки: в базе, в репозитории данных и в том, что прочтёт метаприложение, не меняется ничего. Это правка API ядра, а не договора (Р-51 «Трапезы»): релиза на все приложения сразу она не требует.

**Решено.**

- У `ImportPlan` три поля, **необязательных**:
  - `notes?: Note[]` — запись загрузится, но человеку стоит посмотреть: округление, подозрение, замена. `Note = { section, title, text }`
  - `changed?: Count[]` — сколько уже имеющихся записей изменится
  - `removed?: Count[]` — сколько уйдёт надгробием
- `Count = { count, forms }` — прежний `Added`; `Added` остаётся его синонимом. `mergeResults` сводит новые поля так же, как `added` и `issues`, и отдаёт их всегда
- **Сводка** по порядку: «Добавится» → «Изменится» → «Удалится» → «Уже есть — пропущено» → **«Загрузится, но стоит посмотреть: N»** (не цветом ошибки) → «Не разобрано — в базу не попадёт: N». Счёт отказов — только `issues`
- **Общий абзац** — правда для любого приложения: повторная загрузка ничего не удвоит; если меняется что-то уже имеющееся — сводка назовёт это до записи
- **`ImportSummary({ text, planImport, onApplied, onCancel })`** — сводка и запись, вынесенные из `ImportRecords`: разбирает готовый текст, показывает сводку, пишет по кнопке в порядке `stores` конфига. `ImportRecords` пользуется ею сам; приложение ставит её там, где текст у него появился
- Что правка или удаление, говорит **приложение**, как и `added`: ядро не сравнивает `writes` со слепком

Выбор человека, рекомендация.

**Почему.** Сводка — единственное место, где человек видит, что импорт сделает с его данными, до записи. Отказ, заметка, правка и удаление — четыре разных ответа на «что будет», и слово у каждого своё. Необязательные поля — чтобы приложение без заметок и правок («Трапеза») обновило указатель без единой правки своих разборов.

Отвергнуто:
- **поля обязательными** — строже, но каждый раздел каждого приложения не соберётся, пока в нём не появятся пустые списки;
- **правку и удаление одним `changed`** — «Изменится: 1 итог» прячет, что итог исчезнет; удаление человеку важнее увидеть;
- **считать правки и удаления ядром**, сравнивая `writes` со слепком по `id`, — у ядра нет слов для чужих записей, и у одного числа стало бы два источника;
- **пропс `initialText` у `ImportRecords`** — тянет туда, где появился текст, весь экран импорта с полем, файлом и промптом, либо переход на экран импорта с текстом в состоянии роутера.

**Цена.**

1. Честность сводки держится на приложении: забыло назвать правку — сводка промолчит, как раньше. Ловится тестами разбора приложения.
2. Общий абзац меняется у всех — у «Трапезы» тоже: видимое изменение, строка «Что нового» при обновлении указателя по её выбору.
3. `Count` в `changed` и `removed` — склонение существительного, а не действия: «Изменится: 2 счёта», «Удалится: 1 итог периода».

### Я-08 · Выборка по индексу `db.getByIndex`; индексы хранилищ версии 1 заморожены вместе с `v1Stores`
23.09.2026

Повод: находка Этапа 0 «Злотых» (их Журнал, 20.09.2026) — ядро заводит индексы из `config.indexes`, а читать по ним не даёт: `getAll` читает хранилище целиком. Отложено человеком до конца «Злотых».

**Решено.**

- `db.getByIndex(store, index, match, { includeDeleted? })` — записи хранилища, у которых поле индекса совпало. `match` — ключ (`string | number`) или диапазон `{ from?, to? }`, границы включительно. `IDBKeyRange` не выходит из `core/db.ts`. Надгробия отсеиваются, как у `getAll`
- Индекс проверяется **по базе на устройстве** (`indexNames`), а не по конфигу. Нет его — внятная ошибка с именами хранилища и индекса
- Записи без поля (`null`, не задано) в индекс не попадают — так устроен IndexedDB; сказано в комментарии
- **`indexes` хранилищ версии 1 заморожен вместе с `v1Stores`.** `createStores` заводит их только на свежей базе: индекс, дописанный в конфиг позже, появится у новой установки и не появится у давней, а миграция, заводящая его же, на свежей базе упадёт — индекс уже есть. Индекс после первого релиза — только шагом миграции (`additive: true`). Правило — в комментарии `AppConfig.indexes` и в `02-Архитектура`

Выбор человека, рекомендация.

**Почему.** Индекс, по которому никто не читает, — обещание без применения (Р-32 «Злотых»). История за годы — тысячи записей, и месяц не должен читать их все. Проверка по устройству, а не по конфигу, — потому что конфиг и база могут разойтись ровно так, как описано выше.

Отвергнуто:
- **`IDBKeyRange` наружу** — к IndexedDB ходило бы не только `core/db.ts`;
- **сверять индекс с `config.indexes`** — индексы хранилищ, заведённых миграцией, в конфиге только для чтения глазами, а на устройстве они есть;
- **переименовать поле `indexes`** в честное «не читается» — вместо того чтобы дать читать.

**Цена.** Составных ключей и сортировки по убыванию нет — не понадобились. Правило заморозки держится памятью: `checkConfig` не видит, что было в первом релизе.

### Я-09 · Годовая нарезка в раскладке: `Place` с `split: 'year'`; нарезка места после первого релиза не меняется
24.09.2026

Повод: находка перевода «Делу Время» (Журнал ядра, 24.09.2026), сверенная через `git show a913dcb` «Дневников». Их `cycleEvents` и `content` лежат по годам — `cycles/ГГГГ.json`, `content/ГГГГ.json`, без даты — `undated.json` (Р-08, Р-33, Р-34 «Дневников»). `Place` ядра и договор знали только «одним файлом» и «по месяцам». Переложить их данные по месяцам — миграция репозитория данных, а перевод данных не трогает (Р-49 «Трапезы»): без годовой нарезки «Дневники» не перевести.

**Это правка договора семьи** — раскладку читает метаприложение (Р-51 «Трапезы»). Решение здесь и релиз на все приложения: указатель обновляют все, хотя коду приложений без годовых мест править нечего — `Place` только расширяется.

**Решено.**

- У `Place` третий вид: `{ split: 'year'; dir; dateOf }`. Файл — `<dir>/ГГГГ.json`, год — по дате записи любой точности: день `ГГГГ-ММ-ДД` и месяц `ГГГГ-ММ` (Р-25 «Дневников») дают один год. Без даты и с нечитаемой датой — `<dir>/undated.json`, как у месячной нарезки
- Год в имени файла — **первые четыре знака даты**, а не число: `0999` остаётся `0999.json`, и `storeOf` его узнаёт. У «Дневников» на `a913dcb` год — число из `yearOf`: для лет 1000…9999 файл тот же побайтно, год до 1000 у них дал бы файл, который их же `storeOf` не узнаёт
- `storeOf` годовой папки узнаёт только `ГГГГ.json` и `undated.json`, месячной — только `ГГГГ-ММ.json` и `undated.json`: чужой нарезки файл в папке — не наш и не трогается
- README данных: строка `<dir>/ГГГГ.json`; фраза о непереписываемом прошлом называет годы, если у приложения есть годовые места. У приложения без них README не меняется ни на байт — это закреплено тестом
- **Нарезка места после первого релиза не меняется** — ни вид (`none` / `month` / `year`), ни `dir`, ни путь. Прежние файлы после смены стали бы для `storeOf` чужими: на сервере осталась бы копия, а записи из них не дошли бы до свежего устройства. Смена нарезки — миграция репозитория данных, а не правка конфига. Правило — в комментарии `Place` и в договоре

Выбор человека, рекомендация.

**Почему.** Годовая нарезка — не частность «Дневников»: она нужна хранилищу, в которое пишут редко (отметки цикла, просмотренное), — там месячный файл дробил бы историю на десятки файлов по одной записи. Р-28 «Делу Время» выбрал месяцы для хранилища, куда пишут на каждое нажатие; оба выбора верны для своих хранилищ, и выбирает их приложение полем `places`.

Отвергнуто:
- **переложить данные «Дневников» по месяцам** — миграция данных в переводе, который обязан их не трогать;
- **`split` параметром-функцией** («имя файла по записи») — договор перестал бы быть перечислимым: метаприложение и `storeOf` не знали бы, какие файлы наши;
- **год числом, как у «Дневников»**, — повтор ошибки на годах до 1000 ради побайтного совпадения там, где его и так нет.

**Цена.**

1. Релиз на все приложения без видимого изменения у трёх из них: указатель обновляется ради договора.
2. Правило «нарезка не меняется» держится памятью: `checkConfig` не видит, какой нарезка была в первом релизе.
3. Метаприложение, когда появится, читает три вида файлов, а не два.
